  <name>Task 1: Route Ctrl+A and Shift+arrows for composer selection</name>
  <files>apps/tui/src/composer.rs, apps/tui/src/main.rs, apps/tui/src/mouse.rs</files>
  <action>
1. **composer.rs handle_key()** -- Add a Ctrl+A match arm BEFORE the catch-all `_ =>` arm:
   ```rust
   // Ctrl+A = select all (override tui-textarea's default "move to line start")
   KeyEvent { code: KeyCode::Char('a'), modifiers, .. }
       if modifiers.contains(KeyModifiers::CONTROL) => {
       self.textarea.select_all();
       None
   }
   ```

   Shift+arrows do NOT need special handling -- they already fall through to the `_ => { self.textarea.input(key); None }` catch-all, and tui-textarea automatically starts/extends selection when Shift modifier is present on arrow keys. Verify this is the case by confirming the catch-all exists and passes keys to `textarea.input()`.

   Also ensure the Enter handler (send) clears any active selection by resetting the textarea (it already does `self.textarea = Self::make_textarea(self.active)` which creates a fresh textarea).

2. **main.rs** -- In the global key handler, add Ctrl+A handling that routes to the focused pane. Currently Ctrl+A is handled in the Output pane's focus-specific section (for select-all-output). Add logic so that when `app.focus == Focus::Composer`, Ctrl+A calls `app.composer.select_all()` instead.

   Find the existing `KeyCode::Char('a') if key.modifiers.contains(KeyModifiers::CONTROL)` handler in the Output key section. This should already work because Ctrl+A in Composer goes through `composer.handle_key()` which we just added the Ctrl+A intercept to. BUT verify that Ctrl+A is not caught by a global handler before reaching focus-specific dispatch. If it IS caught globally, add a focus check:
   - `Focus::Composer` -> `app.composer.select_all()`
   - `Focus::Output` -> existing select-all-output logic

3. **mouse.rs** -- In the click handler, when a mouse click lands ANYWHERE (not just in composer area), clear composer selection if it exists. Add after the existing click handling:

   At the TOP of the MouseDown handler (before focus-specific logic), if `app.composer.has_selection()` is true AND the click is NOT in the composer area, cancel the selection. For clicks inside the composer area, tui-textarea handles it via its own click handler.

   In the MouseDown handler, before focus-specific dispatch, add:
   ```rust
   // Clear composer selection on any click outside composer (iTerm2-style)
   if !contains(areas.composer, col, row) && app.composer.has_selection() {
       app.composer.cancel_selection();
   }
   ```

   tui-textarea has `cancel_selection()` method (from 0.7 API). Add `pub fn cancel_selection(&mut self)` to Composer that delegates to `self.textarea.cancel_selection()`. Then call `app.composer.cancel_selection()` on click outside composer.

   Add to Composer impl in composer.rs:
   ```rust
   pub fn cancel_selection(&mut self) {
       self.textarea.cancel_selection();
   }
   ```
